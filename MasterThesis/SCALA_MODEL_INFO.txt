  SCALA — RDFRULES LIBRARY BASELINE (REFERENCE IMPLEMENTATION)

1. PURPOSE
============

The ScalaMeasuring folder provides the ground-truth reference for
support counting.  It uses the RDFRules library — an existing Scala/JVM
open-source project (github.com/propi/rdfrules) — to compute rule
support on the same data and rules as all C++/GPU implementations.

This serves two purposes:

  a) Correctness baseline: the RDFRules library is an established,
     tested implementation of AMIE-style rule mining.  All C++ and GPU
     implementations must produce the same support counts as RDFRules
     (with injectiveMapping = true) to be considered correct.

  b) Performance baseline: measuring how fast the JVM/Scala code
     computes support provides the "before" number that the C++ and
     GPU speedups are measured against.

The ScalaMeasuring code does NOT reimplement support counting.  It is
a thin benchmark harness that:
  - Parses the same rule text files used by C++ implementations
  - Feeds them into the RDFRules library's Ruleset.computeSupport()
  - Measures per-rule and total wall-clock time
  - Outputs results in a format comparable to C++/GPU output


2. WHAT RDFRULES DOES INTERNALLY
===================================

The RDFRules library (com.github.propi.rdfrules) handles:

  2.1 Data Loading and Indexing
  -------------------------------
  Graph(ttlPath).toDataset.index

  This chain:
    - Parses a Turtle (.ttl) file into RDF triples
    - Builds an in-memory Dataset
    - Constructs an Index: internal data structures mapping integer-
      encoded subjects, predicates, and objects for efficient lookup.

  RDFRules uses a TripleIndex internally — a hierarchy of hash maps
  and sorted arrays indexed by (predicate, subject, object) in
  multiple orderings (PSO, POS, SPO, etc.) for fast pattern matching.

  The index is built lazily: internal structures are materialized on
  first access.  This is why the benchmark includes a warmup step.

  2.2 Rule Representation
  -------------------------
  ResolvedRule: a rule with URI-level atoms (not yet integer-encoded).
    - body: IndexedSeq[ResolvedAtom]  (body atoms, e.g. ?a Q ?b)
    - head: ResolvedAtom              (head atom, e.g. ?a P ?b)
    - measures: Seq[Measure]          (Support, HeadCoverage, etc.)

  ResolvedAtom.parse(subj, pred, obj) creates an atom from strings.
  Variables use "?a", "?b", etc.  Predicates are full URIs wrapped
  in angle brackets: <https://w3id.org/biolink/vocab/related_to>.

  2.3 Support Counting (computeSupport)
  ----------------------------------------
  Ruleset(index, rules).computeSupport(minSupport, injectiveMapping)

  This is the core operation being benchmarked.  RDFRules internally:

    - Maps each ResolvedRule's URIs to integer IDs via the Index
    - For each rule, iterates over all head triples (s, p, o) where
      p = head predicate
    - For each head triple, binds head variables and attempts to
      satisfy all body atoms via backtracking search
    - Counts how many head triples have at least one satisfying
      body instantiation

  Key parameters:
    - minSupport = 1: keep all rules (even with support = 1)
    - injectiveMapping = true: no two distinct variables may map to
      the same entity.  This is the standard AMIE semantics.

  The library handles:
    - Greedy atom ordering (most-bound-first)
    - Injective variable binding checks
    - Early termination (existential: stop after first body match)

  2.4 Parallelism Control
  -------------------------
  Ruleset.setParallelism(1) forces single-threaded execution.
  This is used in the benchmark for two reasons:
    - Memory: Colab's 12 GB RAM is tight; parallel execution would
      require multiple index copies or concurrent data structure access
    - Fair comparison: the C++ CPU implementations also run
      single-threaded (CPU_01_nonparallel) for the primary benchmark

  2.5 Streaming Evaluation
  --------------------------
  RDFRules uses lazy evaluation.  The call chain:
    ruleset.computeSupport(...).resolvedRules.foreach { r => ... }

  processes rules one at a time in a streaming fashion.  Each rule is
  computed, emitted to the callback, then the next rule is processed.
  This means per-rule timing is measured by recording nanoTime between
  successive callback invocations.

3.1 build.sbt
---------------
  name := "scala-measuring"
  scalaVersion := "2.13.8"

  Key configuration:
    - dependsOn(rdfrules_core): compiles against a local checkout of
      the RDFRules repository (cloned in Colab at /content/rdfrules)
    - fork := true: runs in a separate JVM process
    - javaOptions += "-Xmx10g": allocates up to 10 GB heap

  The project uses ProjectRef to reference the RDFRules "core" module
  directly from source, avoiding published artifact version mismatches.

3.2 SupportBenchmark.scala
-----------------------------
  A single-file Scala application (~200 lines) with:

  a) Rule parsing:
     - expandUri(): expands prefix shorthands (biolink:, rdf:, rdfs:,
       owl:) to full URIs matching the C++ RuleParser's prefix map
     - parseAtom(): converts "( ?a biolink:pred ?b )" into a
       ResolvedAtom using RDFRules' ResolvedAtom.parse()
     - parseRuleLine(): splits a rule line at "=>" into head and body,
       extracts atoms and measures from the text format

  b) Benchmark flow (main):
     Step 1: Load TTL and build Index (timed)
     Step 2: Parse rules from text file into ResolvedRule objects
     Step 3: Warmup — run 1 throwaway rule to force lazy index init
     Step 4: Create Ruleset with setParallelism(1)
     Step 5: computeSupport(minSupport=1, injectiveMapping=true)
             with per-rule timing via nanoTime delta

  c) Output:
     - Per-rule: support, head coverage, head support, head size, time
     - Summary: index build time, warmup time, total support time,
       avg/median/min/max/P95 per-rule times
     - Statistics grouped by body size

5. RELATIONSHIP TO OTHER IMPLEMENTATIONS
===========================================

  Scala (RDFRules)       — THIS: reference baseline, ground truth
      |
      v
  Rewritten_CPP          — Faithful C++ port of RDFRules' data
      |                    structures (nested hash maps).
      |                    Same algorithm, same support counts.
      v
  CPU_01_nonparallel     — Optimized C++: flat sorted arrays + CSR,
      |                    zero-allocation DFS, template specialization.
      |                    Same support counts, much faster.
      v
  CPU_01_parallel        — CPU_01 with OpenMP parallelism.
      |                    Same support counts.
      v
  GPU_01                 — Sorted int2 arrays on GPU, __constant__
      |                    memory, warp-cooperative DFS.
      v
  GPU_03                 — CSR on GPU (O(1) row access), best of
                           GPU_01 + GPU_02.  Same support counts.

  GPU_02 (separate path) — Sparse-matrix chain approach.
                           Does NOT enforce full injective mapping
                           on intermediate chain variables.
                           May overcount on multi-body rules.

All implementations (except GPU_02) produce identical support counts
when run on the same data and rules, with the Scala/RDFRules output
serving as the authoritative reference.


6. KEY OBSERVATIONS
=====================

6.1 What RDFRules gives us
-----------------------------
  - Correct support counting with AMIE semantics
  - Injective mapping enforcement
  - Greedy atom ordering heuristic
  - Lazy index construction
  - Parallelism control

6.2 What the benchmark harness adds
--------------------------------------
  - Rule parsing from text files (rules mined by external AMIE runs)
  - Per-rule timing measurement via streaming evaluation
  - Prefix expansion matching the C++ implementations
  - Memory-optimized execution (kill SBT, direct java invocation)

6.3 Performance characteristics
----------------------------------
  - JVM startup + JIT compilation adds overhead to early rules
  - The warmup step mitigates lazy index initialization but not JIT
  - Single-threaded execution avoids GC pressure from parallel work
  - Index build time is comparable to C++ (both dominated by I/O
    and hash map construction)
  - Support counting is significantly slower than optimized C++ due
    to JVM overhead: object allocation, garbage collection, lack of
    cache-friendly flat arrays, no template specialization


7. DATA STRUCTURES AT EACH STAGE
===================================

7.1 After Step 1 (Graph loading)
----------------------------------
  Graph(ttlPath).toDataset.index

  The TTL file is parsed into raw triples in memory, but the actual
  index structures are NOT built yet.  The Index object holds a lazy
  reference to the dataset.  No hash maps exist at this point.

7.2 After Step 2 (Rule parsing)
---------------------------------
  resolvedRules: IndexedSeq[ResolvedRule]

  Rules are stored as ResolvedRule objects with STRING-level atoms:
    ResolvedRule(
      body = [ResolvedAtom("?a", "<https://w3id.org/biolink/vocab/treats>", "?b")],
      head = ResolvedAtom("?a", "<https://w3id.org/biolink/vocab/affects>", "?c"),
      measures = [Support(42), HeadCoverage(0.05)]
    )
  Variables are strings ("?a"), predicates are full URI strings.

7.3 After Step 3 (Warmup — lazy index materialization)
--------------------------------------------------------
  The first call to computeSupport triggers buildAll, which constructs:

  A) TripleItemIndex — bidirectional URI-to-integer dictionary:
       "biolink:treats" <-> 7
       "biolink:affects" <-> 12
       "entity_John"    <-> 42
     Every unique URI/entity in the 6.8M triples gets a compact int.

  B) TripleIndex — three nested hash map structures:

     1. predicates: HashMap[int_pred -> PredicateIndex]   (MAIN INDEX)
        Each PredicateIndex contains:
          - subjects (PSO): HashMap[int_subj -> HashSet{int_obj, ...}]
            "Given predicate P and subject S, what objects exist?"
          - objects  (POS): HashMap[int_obj  -> HashSet{int_subj, ...}]
            "Given predicate P and object O, what subjects exist?"

        Example in RAM:
          predicates:
            pred_7 -> PredicateIndex
              subjects: { subj_42 -> {obj_1, obj_5, obj_99},
                          subj_88 -> {obj_3} }
              objects:  { obj_1 -> {subj_42, subj_77},
                          obj_3 -> {subj_88} }
            pred_12 -> PredicateIndex
              subjects: { ... }
              objects:  { ... }

     2. subjects: HashMap[int_subj -> SubjectIndex]   (AUXILIARY)
          SubjectIndex contains: predicates: HashSet{pred_7, pred_12, ...}
          "Which predicates does this subject appear with?"

     3. objects: HashMap[int_obj -> ObjectIndex]       (AUXILIARY)
          ObjectIndex contains: predicates: HashSet{pred_7, ...}
          "Which predicates does this object appear with?"

     Only structure #1 (predicates) is used for support counting.
     Structures #2 and #3 are used for neighbour statistics and
     cardinality computation.

  C) Lazy statistics inside each PredicateIndex (built on first access):
       - neighboursSS/SO/OO/OS: predicate co-occurrence counts
       - averageSubjectCardinality, averageObjectCardinality
       - lowerCardinalitySide, higherCardinalitySide
     These are used for confidence measures, not support counting.

7.4 After Step 4 (Ruleset creation)
--------------------------------------
  Ruleset(index, ForEach.from(resolvedRules)).setParallelism(1)

  Rules are converted from ResolvedRule (strings) to FinalRule (ints):
    FinalRule(
      head = Atom(Variable(0), 12, Variable(2)),    // ?a pred_12 ?c
      body = [Atom(Variable(0), 7, Variable(1))],   // ?a pred_7  ?b
      measures = {Support->0, HeadSize->0, HeadSupport->0, HeadCoverage->0.0}
    )

  Atom fields:
    - predicate: int (e.g. 7 = "biolink:treats")
    - subject: Variable(0) = ?a, Variable(1) = ?b, or Constant(42)
    - object:  same — Variable or Constant, all ints

  The Ruleset is lazy (ForEach wrapper) — rules are converted on demand.

7.5 During Step 5 (Support counting loop)
--------------------------------------------
  ruleset.computeSupport(minSupport=1, injectiveMapping=true)
    .resolvedRules.foreach { r => ... }

  This is a pull-based stream. For each rule in sequence:
    1. Take the FinalRule (integer atoms)
    2. Look up head predicate in predicates index
    3. Iterate all (subject, object) pairs for that predicate
    4. For each head pair, bind head variables and run DFS backtracking
       through body atoms using the predicates index (PSO/POS lookups)
    5. If at least one full body instantiation exists -> support++
    6. Enforce injective mapping: no two distinct variables may bind
       to the same entity
    7. Emit the rule with updated Support/HeadCoverage/HeadSupport/HeadSize
    8. .resolvedRules converts int atoms back to string atoms using
       TripleItemIndex for printing
    9. The foreach body records timing and prints results

  Per-rule timing is measured as nanoTime delta between consecutive
  rule emissions from the lazy stream.
