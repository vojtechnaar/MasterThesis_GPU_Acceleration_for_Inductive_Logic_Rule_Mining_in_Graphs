================================================================================
  GPU_01 — BINARY-SEARCH DFS WITH __CONSTANT__ MEMORY AND WARP-COOPERATIVE KERNELS
================================================================================

1. PURPOSE AND RELATIONSHIP TO CPU_01
=======================================

GPU_01 is the first GPU implementation of support counting.  It ports
the CPU_01 algorithm (template-specialized DFS with greedy atom ordering)
to CUDA, replacing CPU data structures with GPU-friendly equivalents:

  CPU_01 PredIndex (CSR)     →  sorted int2 arrays per predicate (SPO/POS)
  CPU_01 stack-local Env     →  thread-local int v[MAXVAR] in registers
  CPU_01 template DFS<N>     →  GPU __device__ template dfs<L,N>()
  CPU_01 sequential head     →  thousands of GPU threads, one per head triple
  iteration                     (standard kernel) or one warp per head triple
                                (warp-cooperative kernel)

The GPU achieves parallelism at the head-triple level: instead of
iterating head triples sequentially, all head triples for a rule are
distributed across GPU threads.  Rules themselves are processed
sequentially (one kernel launch per rule).

3. DATA STRUCTURES
====================

3.1 PredHost / PredDev (per-predicate sorted int2 arrays)
-----------------------------------------------------------
Unlike CPU_01's CSR format (three separate arrays: keys, offsets, vals),
GPU_01 uses a simpler representation — sorted arrays of int2 pairs:

  struct PredHost {
      std::vector<int2> spo;    // sorted (subject, object) pairs
      std::vector<int2> pos;    // sorted (object, subject) pairs
      int spo_maxfan;           // max values sharing one key in SPO
      int pos_maxfan;           // max values sharing one key in POS
  };

  struct PredDev {
      int2* spo;   int spo_n;   // device pointer + count for SPO
      int2* pos;   int pos_n;   // device pointer + count for POS
  };

Why sorted int2 instead of CSR?

  a) Simplicity: only one array to upload per direction, not three.
  b) Memory overhead: CSR requires an extra rowPtr array of size
     nEntities+1 (~2MB for 500K entities).  Sorted int2 has zero
     overhead beyond the pairs themselves.
  c) Random access: GPUs handle binary search well when the array
     fits in L2 cache or texture cache (__ldg).
  d) Trade-off: locating a key's range requires two binary searches
     (lower_bound + upper_bound) at O(log |P|) where |P| is the
     number of pairs for the predicate.  CSR would give O(1) row
     access.

The maxfan field records the maximum fan-out (max values per key) and
is used to decide between the standard and warp-cooperative kernels.

3.2 build_gpu_index() — construction from RdfIndexes
------------------------------------------------------
  Input:  CPU_01's RdfIndexes (with PredIndex per predicate)
  Output: unordered_map<int, PredHost>

  For each predicate:
    1. SPO: copy PredIndex.spo (already sorted+deduped pair<int,int>)
            into a vector<int2>
    2. POS: reverse each (s,o) to (o,s), sort, deduplicate
    3. Compute maxfan for both directions

3.3 upload() — GPU memory transfer
-------------------------------------
  For each predicate, cudaMalloc + cudaMemcpy the int2 arrays to GPU
  global memory.  Returns unordered_map<int, PredDev> with device
  pointers.

3.4 AtomGPU (per-atom descriptor in __constant__ memory)
----------------------------------------------------------
  struct AtomGPU {
      const int2* arr;      // device pointer to sorted (key, val) array
      int         n;        // array length
      int         keySlot;  // variable slot holding the lookup key
      int         valSlot;  // variable slot to bind (-1 = fully bound)
      int         chkSlot;  // variable slot to check (-1 = enumerating)
  };

  __constant__ AtomGPU c_atoms[MAX_BODY];   // MAX_BODY = 8

Before each kernel launch, the host copies this rule's atom descriptors
into __constant__ memory via cudaMemcpyToSymbol.  This means:

  a) All threads in the kernel read the same atom descriptors, so
     __constant__ memory is broadcast to all threads in a warp in a
     single cache-line read.
  b) Only 5 fields × 8 atoms × 4 bytes ≈ 160 bytes — fits easily in
     the 64KB __constant__ cache.
  c) No function arguments needed to pass atom info — the kernel reads
     directly from c_atoms[L] where L is known at compile time.

3.5 GpuRule / GpuBodyAtom — CPU-side rule representation
-----------------------------------------------------------
  struct GpuBodyAtom { int pred, sVar, oVar; };
  struct GpuRule {
      int headPred, hS, hO;     // head predicate, subject/object slots
      std::vector<GpuBodyAtom> body;
      int numVars;
  };

convert_rule(FinalRule) → GpuRule:
  - Variables keep their original slot IDs (0, 1, 2, ...)
  - Constants get "virtual" variable slots starting at maxVarId+1
  - numVars = total number of slots (determines v[] array bounds)


4. THE GPU DFS ALGORITHM
==========================

4.1 Binary search with __ldg (texture cache)
-----------------------------------------------
Two helper functions provide lower-bound and upper-bound search over
sorted int2 arrays, using __ldg() for read-only texture cache:

  __device__ int lb(const int2* a, int n, int k);   // lower bound on .x
  __device__ int ub(const int2* a, int n, int k);   // upper bound on .x

__ldg() tells the GPU hardware to route reads through the read-only
texture cache (separate from L1), which is optimized for spatially
scattered reads.  This is beneficial because different threads in a
warp typically search for different keys → scattered access.

Cost per lookup: O(log |P|) where |P| = number of pairs for the
predicate (e.g. 500K for rdf:type).  For log₂(500K) ≈ 19 iterations,
each with an __ldg read, this is ~38 memory reads to locate a key's
range.

4.2 Template DFS<L, N>()
---------------------------
  template <int L, int N>
  __device__ bool dfs(int v[MAXVAR]);

L = current body atom index (0, 1, ..., N-1)
N = total body atoms (known at compile time)

Base case: L == N → return true (all body atoms matched).

Recursive case for atom c_atoms[L]:
  1. Compute key = v[a.keySlot]  (the bound variable to look up)
  2. lo = lb(a.arr, a.n, key)    (binary search for range start)
     hi = ub(a.arr, a.n, key)    (binary search for range end)
  3. If lo == hi → no entries for this key → return false

  If fully bound (valSlot < 0):
    Binary search colInd[lo..hi) for v[chkSlot].  If found, recurse
    to dfs<L+1, N>.

  If enumerating (valSlot >= 0):
    For each entry in [lo, hi):
      a. Read val = __ldg(&a.arr[i].y)
      b. Injective mapping check: skip if val already bound elsewhere
         (#pragma unroll over MAXVAR slots)
      c. Bind: v[valSlot] = val
      d. Recurse: if dfs<L+1, N>(v) → restore and return true
      e. Backtrack: v[valSlot] = old

Key properties:
  - L is a compile-time constant, so the compiler unrolls the entire
    DFS chain for small N (1–3 body atoms → full inlining)
  - The v[] array lives in GPU registers (16 ints = 64 bytes)
  - No heap/stack allocation on the GPU — all state in registers
  - Injective mapping check is a #pragma unroll loop over MAXVAR=16
    slots, compiled to 16 register comparisons

4.3 Standard kernel: 1 thread per head triple
------------------------------------------------
  template <int N>
  __global__ void support_kernel(
      const int2* head, int headN,
      int hS, int hO, unsigned long long* out);

Each thread:
  1. Initialize v[MAXVAR] = {-1, ...}
  2. Bind head variables: v[hS] = head[i].x, v[hO] = head[i].y
  3. Call dfs<0, N>(v)
  4. If true → increment local counter

After the grid-stride loop, threads perform warp-level reduction
using __shfl_down_sync followed by a single atomicAdd per warp to
the global result counter.

Launch parameters:
  blockDim = 256, gridDim = min(ceil(headN/256), 2048)
  __launch_bounds__(256, 2) — hints for register allocation

4.4 Warp-cooperative kernel: 1 warp per head triple
------------------------------------------------------
  template <int N>
  __global__ void support_kernel_coop(
      const int2* head, int headN,
      int hS, int hO, unsigned long long* out);

When the first body atom has high fan-out (maxfan > COOP_FAN = 64),
32 threads (one warp) collaborate on a single head triple.  Each
thread (lane) handles a different slice of the first atom's candidates.

Logic:
  1. All 32 lanes load the same head triple (v[hS], v[hO])
  2. Compute the range [lo, hi) for the first atom's key
  3. Split the range across 32 lanes: lane k handles indices
     base+k for base = 0, 32, 64, ...
  4. Each lane independently:
     - Reads a candidate value, checks injectivity
     - If valid, binds it and calls dfs<1, N>(v) for remaining atoms
  5. __any_sync(0xFFFFFFFF, found): if ANY lane found support,
     the warp early-exits and moves to the next head triple:
     - Only lane 0 increments the counter
     - All lanes skip remaining candidates for this head triple

Why 32 threads (1 warp)?
  - CUDA warps execute in lock-step — no synchronization needed
  - __any_sync is a single hardware instruction
  - Prevents warp divergence: if one lane finds support, the
    __any_sync early-exit prevents the other 31 lanes from doing
    redundant work

Fully-bound first atom: only lane 0 performs the existence check
(the other 31 lanes idle).  This is rare and harmless — fully-bound
first atoms have zero fan-out.

4.5 Kernel selection (standard vs warp-cooperative)
-----------------------------------------------------
  if (ord[0].valSlot >= 0):     // first atom enumerates
      maxfan = spo_maxfan or pos_maxfan of first atom's predicate
      useCoop = (maxfan > COOP_FAN)    // COOP_FAN = 64

  useCoop = true  → launch support_kernel_coop  (1 warp per head triple)
  useCoop = false → launch support_kernel        (1 thread per head triple)

The threshold (64) balances: below 64 candidates, warp-coop wastes
lanes; above 64, the parallelism over candidates pays off.


5. BODY ATOM ORDERING (maxfan-aware greedy)
=============================================

  order_body(GpuRule, PredHost map) → vector<Ordered>

Same greedy heuristic as CPU_01 (pick the atom with the most bound
variables, break ties by lowest candidate count), but tailored for
the GPU warp-cooperative kernel:

  struct Ordered {
      int pred;
      int keySlot, valSlot, chkSlot;
      bool useSPO;    // true = SPO array, false = POS array
  };

The atom placed at position 0 is special: it is the one parallelized
across 32 warp lanes in the coop kernel.  The ordering prefers high-
fan-out atoms at position 0 to maximize warp utilization.

Key scoring rules for each unscheduled atom:
  - Both bound (sh=2): score = total pair count (will be checked, not enumerated)
  - Subject bound (sh=1): use SPO array, score = spo_maxfan
  - Object bound (sh=1): use POS array, score = pos_maxfan
  - Neither bound (sh=0): skip (not yet reachable from bound variables)

Higher sh (more bound variables) is always preferred.  Within the same
sh, lower candidate count is preferred (fewer iterations).

After ordering, each Ordered entry has:
  - keySlot: the bound variable to look up
  - valSlot: the variable to bind (-1 if both bound → existence check)
  - chkSlot: the variable to check (-1 if enumerating)
  - useSPO:  true = SPO direction, false = POS direction


6. EXECUTION FLOW
===================

  1. Parse Turtle file with raptor2 → RdfIndexes (CPU_01 format)
  2. build_gpu_index() → PredHost per predicate (sorted int2 arrays)
  3. upload() → PredDev per predicate (device pointers)
  4. Parse rules → vector of FinalRule
  5. convert_rule() → GpuRule per rule (slot assignment)
  6. For each rule:
     a. Compute headSize, headSupport (via PredIndex CSR, same as CPU)
     b. order_body() → ordered atom list with keySlot/valSlot/chkSlot
     c. Build AtomGPU[nb] → upload to __constant__ c_atoms[]
     d. Decide standard vs warp-cooperative (maxfan > COOP_FAN?)
     e. cudaEventRecord(start)
     f. Launch kernel (support_kernel<N> or support_kernel_coop<N>)
     g. cudaEventRecord(stop), cudaEventSynchronize(stop)
     h. Read result from device (cudaMemcpy d_res → sup)
     i. Set rule measures (support, headCoverage, headSupport, headSize)
  7. Print results and timing statistics


7. GPU-SPECIFIC OPTIMIZATIONS
===============================

  a) __constant__ memory for atom descriptors:
     All threads in a kernel need the same atom info.  __constant__
     memory is broadcast from cache → no memory traffic.

  b) __ldg() for data reads:
     All binary searches and data reads use __ldg() to route through
     the read-only texture cache, which handles scattered access well.

  c) Register-only v[] array:
     The MAXVAR=16 int array fits in 64 bytes of register space.
     No shared memory or global memory needed for DFS state.

  d) Warp reduction:
     The global support counter uses __shfl_down_sync for intra-warp
     reduction, then atomicAdd once per warp.  This reduces atomic
     contention from one atomicAdd per thread to one per warp (8×
     reduction for 256-thread blocks).

  e) Grid-stride loop:
     Each kernel uses a grid-stride loop, so the GPU can launch a
     fixed number of blocks and have threads process multiple head
     triples.  Avoids launching an excessively large grid.

  f) __launch_bounds__(256, 2):
     Tells nvcc each block uses 256 threads, with target occupancy
     of 2 blocks per SM.  This guides register allocation — allows
     more registers per thread (since fewer blocks share the SM).

  g) CUDA events for timing:
     cudaEventRecord/Elapsed provides sub-millisecond GPU timing
     that excludes CPU overhead.


8. COMPARISON WITH CPU_01
============================

               CPU_01_nonparallel        GPU_01
               ------------------        ------
Index format   CSR (3 arrays)            sorted int2 (1 array)
Row access     O(1) via offsets[]        O(log |P|) binary search
DFS            stack-local Env (176B)    register int v[16] (64B)
DFS template   dfsExists<N> (CPU)        dfs<L,N> (GPU __device__)
Head iteration sequential (1 core)       parallel (thousands of threads)
Atom tracking  uint8_t bitmask           compile-time (template L tracks)
Atom ordering  greedy, CSR-based         greedy, maxfan-based
Injective      loop over v[]             #pragma unroll over MAXVAR
Warp-coop      N/A                       32 lanes split 1st atom range
Kernel timing  chrono::high_res          cudaEventElapsedTime

10. WHAT CHANGES FROM CPU_01
===============================

  Data structure:
    OLD: PredIndex with CSR (spoKeys/spoOffsets/spoVals)
    NEW: sorted int2 arrays per predicate (spo[], pos[])

  Execution model:
    OLD: sequential iteration over head triples on 1 CPU core
    NEW: thousands of GPU threads process head triples in parallel

  DFS state:
    OLD: stack-local Env struct (176 bytes, CPU stack)
    NEW: register-local int v[MAXVAR] (64 bytes, GPU registers)

  Atom descriptors:
    OLD: inline PredIndex* pointer + switch cases in DFS
    NEW: AtomGPU in __constant__ memory, read via c_atoms[L]

  Kernel types:
    NEW: standard kernel (1 thread/head triple) for low-fanout atoms
    NEW: warp-cooperative kernel (32 threads/head triple) for high-fanout

  Memory access pattern:
    OLD: sequential L1/L2 cache-friendly iteration
    NEW: scattered global memory reads via __ldg texture cache

  Timing:
    OLD: chrono::high_resolution_clock
    NEW: cudaEvent for GPU kernel time
