Recommendations:
1. Eliminate heap allocations in DFS (biggest win)
Currently extendBindingForAtom allocates a vector<BindingMap> where each BindingMap contains 3 heap-allocated containers (unordered_map, two unordered_sets). This happens at every recursive step. Instead:

Use backtracking with mutation — bind variables, recurse, unbind (like CPU04 does)
Use fixed-size arrays for bindings (rules have at most ~5 variables) instead of hash maps
Use a small fixed array for used atoms instead of unordered_set<UsedTriple>
2. Flat sorted arrays instead of hash maps for indexes
Replace unordered_map<int, unordered_set<int>> (PSO/POS) with sorted vector<pair<int,int>> per predicate + binary search or CSR (Compressed Sparse Row). Much better cache locality, far fewer allocations. This is what CPU04 does.

3. Parallelism over head triples (easy win)
Each head triple is independent — this is embarrassingly parallel. Add #pragma omp parallel for reduction(+:support) over the head triple loop. Scales linearly with cores.

4. Early pruning with minSupport
The Scala version stops early: if currentSupport + remainingHeadTriples < minSupport, it aborts. Your C++ always processes all head triples. Add this check.

5. Bitmask for body atom tracking
Replace vector<bool> used with a uint8_t bitmask (rules have ≤8 body atoms). Cheaper to copy, compare, and manipulate.

6. Template on body size
Like CPU04's dfs_exists<N>, template the DFS on the number of body atoms. The compiler unrolls loops and eliminates branches for known N=3, 4, 5.

7. Worst-case optimal joins
For complex multi-way joins, algorithms like Leapfrog Triejoin can be asymptotically faster than the current nested-loop DFS approach. Requires a trie-based index but handles high-arity joins much better.

8. GPU (CUDA)
Move the head-triple loop to GPU. Each CUDA thread checks one head triple. Body DFS is short (3-5 atoms) so fits in registers. Your notebook names suggest you've already explored this direction.
