================================================================================
  GPU_03 — CSR-INDEXED DFS WITH __CONSTANT__ MEMORY (HYBRID OF GPU_01 + GPU_02)
================================================================================

1. PURPOSE AND DESIGN RATIONALE
==================================

GPU_03 combines the best elements of GPU_01 and GPU_02:

  From GPU_02 (the sparse-matrix approach):
    CSR data structure → O(1) row access via rowPtr[entity]

  From GPU_01 (the DFS approach):
    __constant__ AtomGPU descriptors
    Template-specialized DFS (dfs<L,N>)
    Warp-cooperative kernel with __any_sync early-exit
    __ldg texture cache for all global memory reads
    Full injective mapping enforcement

The key insight: GPU_02's SpGEMM idea failed, but its CSR data
structure is strictly superior to GPU_01's sorted int2 arrays for
per-entity lookups.  GPU_01's kernel optimizations (__constant__,
templates, warp-coop) are strictly superior to GPU_02's fused kernel.
GPU_03 takes the best of both.

Per-atom lookup improvement over GPU_01:

  GPU_01: lb(arr, n, key) + ub(arr, n, key) = 2 × O(log |P|) reads
  GPU_03: rowPtr[key] + rowPtr[key+1]        = 2 reads (O(1))

  For rdf:type with |P| ≈ 500K:
    GPU_01: ~2 × 19 = 38 memory reads (binary search)
    GPU_03: 2 memory reads (direct index)

  For existence checks (both endpoints bound):
    GPU_01: O(log |P|) to find key range, then O(log d) binary search
    GPU_03: O(1) to get range, then O(log d) binary search
    where d = entity degree (typically 1–50, much smaller than |P|)

3. DATA STRUCTURES
====================

3.1 DevCSR (per-predicate CSR matrix with maxfan)
----------------------------------------------------
  struct DevCSR {
      int  rows;
      int  nnz;
      int* d_rowPtr;    // rows+1 entries on device
      int* d_colInd;    // nnz entries on device, sorted within each row
      int  maxfan;      // max entries in any single row
  };

Compared to GPU_02's DevCSR:
  - REMOVED: cols, int64_t nnz, ownsMemory (unused complexity)
  - ADDED:   maxfan (needed for warp-coop kernel decision, from GPU_01)

3.2 PredCSR (per-predicate pair of CSR matrices)
---------------------------------------------------
  struct PredCSR {
      DevCSR spo;   // M: subject→object
      DevCSR pos;   // M^T: object→subject
  };

Same concept as GPU_02, but with the simplified DevCSR struct.

3.3 build_one_csr() — construction
-------------------------------------
  Input:  PredIndex.spo (sorted pair<int,int>), nRows (= nEntities),
          transpose flag
  Output: DevCSR on GPU

  Steps:
    1. If transpose: swap (s,o) → (o,s)
    2. Sort and deduplicate
    3. Build host CSR arrays (rowPtr, colInd)
    4. Compute maxfan = max(rowPtr[i+1] - rowPtr[i] for all i)
    5. cudaMalloc + cudaMemcpy both arrays to GPU

This is cleaner than GPU_02's build_pred_csr() (no ownsMemory flag,
no int64_t nnz, computes maxfan inline).

3.4 CompactHead (flat head triple array)
-------------------------------------------
  struct CompactHead {
      int2* d_pairs;
      int   nPairs;
  };

  build_compact_head(PredIndex&):
    Directly converts PredIndex.spo to int2 pairs and uploads.
    Unlike GPU_02 (which downloads from DevCSR then re-uploads),
    GPU_03 builds from the host-side PredIndex — avoiding a
    wasteful GPU→CPU→GPU round-trip.

3.5 AtomGPU (CSR-based descriptor in __constant__ memory)
------------------------------------------------------------
  struct AtomGPU {
      const int* rowPtr;    // CSR row pointers
      const int* colInd;    // CSR column indices
      int        keySlot;   // variable slot for lookup entity
      int        valSlot;   // variable slot to bind (-1 = fully bound)
      int        chkSlot;   // variable slot to check (-1 = enumerating)
  };

  __constant__ AtomGPU c_atoms[MAX_BODY];

This is the key structural change from GPU_01's AtomGPU:

  GPU_01 AtomGPU:                GPU_03 AtomGPU:
    const int2* arr;               const int* rowPtr;
    int         n;                 const int* colInd;
    int         keySlot;           int        keySlot;
    int         valSlot;           int        valSlot;
    int         chkSlot;           int        chkSlot;

GPU_01 stores a single pointer + length to a sorted int2 array.
GPU_03 stores two pointers (rowPtr, colInd) — the CSR representation.

Both fit comfortably in __constant__ memory:
  GPU_01: 5 fields × 8 atoms × 4 bytes = 160 bytes
  GPU_03: 5 fields × 8 atoms × 4–8 bytes ≈ 192 bytes (pointers are 8B)
  __constant__ cache: 64 KB


4. THE GPU DFS ALGORITHM (CSR VARIANT)
=========================================

4.1 Template DFS<L, N>() — O(1) row access
----------------------------------------------
  template <int L, int N>
  __device__ bool dfs(int v[MAXVAR]);

The DFS structure is identical to GPU_01, but the key lookup is
fundamentally different:

  GPU_01 (sorted int2):
    const int key = v[a.keySlot];
    const int lo  = lb(a.arr, a.n, key);    // O(log |P|) binary search
    const int hi  = ub(a.arr, a.n, key);    // O(log |P|) binary search

  GPU_03 (CSR):
    const int key = v[a.keySlot];
    const int lo = __ldg(&a.rowPtr[key]);     // O(1) single read
    const int hi = __ldg(&a.rowPtr[key + 1]); // O(1) single read

After obtaining [lo, hi), the rest of the DFS is identical:

  If fully bound (valSlot < 0):
    Binary search colInd[lo..hi) for v[chkSlot].
    Note: the range [lo, hi) has size d (entity degree), NOT |P|.
    So the binary search is O(log d) regardless of GPU_01 vs GPU_03.
    The improvement is only in obtaining lo and hi.

  If enumerating (valSlot >= 0):
    Iterate colInd[lo..hi), check injectivity, bind, recurse.
    This is identical to GPU_01's loop over arr[lo..hi).y values.

4.2 Standard kernel — identical to GPU_01
-------------------------------------------
  template <int N>
  __global__ void support_kernel(
      const int2* head, int headN,
      int hS, int hO, unsigned long long* out);

1 thread per head triple, grid-stride loop, warp reduction.
Only the DFS function body differs (CSR lookups vs binary search).

4.3 Warp-cooperative kernel — identical to GPU_01
----------------------------------------------------
  template <int N>
  __global__ void support_kernel_coop(
      const int2* head, int headN,
      int hS, int hO, unsigned long long* out);

32 lanes split the first atom's range.  __any_sync early-exit.

The O(1) row access is particularly beneficial here:
  GPU_01 coop: each of 32 lanes does lb() + ub() = 38 reads for rdf:type
  GPU_03 coop: each of 32 lanes does 2 reads for rowPtr[key]/rowPtr[key+1]
  But all 32 lanes read the SAME key, so GPU_01's __ldg cache may serve
  all 32 in a single cache miss.  The improvement may be smaller than
  the raw O(1) vs O(log n) suggests, due to warp broadcast.


5. BODY ATOM ORDERING (CSR maxfan)
=====================================

  order_body(GpuRule, PredCSR map) → vector<Ordered>

Same greedy algorithm as GPU_01, but scores are computed from
CSR maxfan instead of sorted-array maxfan:

  GPU_01: c = spo_maxfan from PredHost (sorted int2 array)
  GPU_03: c = spo.maxfan from DevCSR (CSR rowPtr max row width)

These values are equivalent (both measure the maximum number of
values sharing one key), so the ordering is identical for the
same rules and data.


6. EXECUTION FLOW
===================

  1. Parse Turtle file with raptor2 → RdfIndexes (CPU_01 format)
  2. build_all_csr() → PredCSR per predicate (CSR on GPU)
  3. Parse rules → vector of FinalRule
  4. convert_rule() → GpuRule per rule (slot assignment)
  5. For each rule:
     a. Compute headSize, headSupport (via PredIndex, same as CPU)
     b. build_compact_head() from PredIndex (if not cached)
     c. order_body() → ordered atom list using CSR maxfan
     d. Build AtomGPU[nb] with rowPtr/colInd → cudaMemcpyToSymbol
     e. Decide standard vs warp-cooperative (maxfan > COOP_FAN?)
     f. Launch kernel (support_kernel<N> or support_kernel_coop<N>)
     g. cudaEventRecord + cudaEventSynchronize for timing
     h. Read result from device, set rule measures
  6. Print results and timing statistics


7. COMPARISON WITH GPU_01 AND GPU_02
=======================================

               GPU_01              GPU_02              GPU_03
               ------              ------              ------
Data format    sorted int2         CSR (full)          CSR (simplified)
Row access     O(log |P|)          O(1)                O(1)
GPU memory     pairs only          rowPtr + colInd     rowPtr + colInd
__constant__   AtomGPU(arr,n)      not used            AtomGPU(rowPtr,colInd)
Template DFS   dfs<L,N>            runtime recursion   dfs<L,N>
Warp-coop      yes (32 lanes)      no                  yes (32 lanes)

GPU_03 inherits:
  From GPU_01: kernel design, __constant__, templates, warp-coop, __ldg
  From GPU_02: CSR data structure (O(1) row access, CompactHead)


8. WHERE GPU_03 SHOULD BE FASTER THAN GPU_01
===============================================

  a) First atom key lookup (every thread, every head triple):
     2 reads vs 2 × O(log |P|) reads.
     Greatest impact for large predicates (rdf:type ≈ 500K pairs).

  b) Existence checks for fully-bound atoms:
     rowPtr gives the range instantly → then O(log d) binary search
     in a small neighborhood (d ≈ entity degree, typically 1–50).
     GPU_01 first does O(log |P|) to find the range, then O(log d).

  c) Reduced register pressure for DFS:
     GPU_01's lb/ub functions iterate with lo/hi/m variables.
     GPU_03's rowPtr access uses two single reads, freeing registers.


9. WHERE GPU_03 MIGHT NOT BE FASTER THAN GPU_01
==================================================

  a) GPU_01's __ldg texture cache:
     When many threads in a warp search for different keys in the same
     sorted int2 array, the O(log n) binary searches may hit the texture
     cache for shared sub-ranges, amortizing the cost.

  b) Memory bandwidth:
     CSR rowPtr arrays are large (~2MB per predicate per direction).
     If many predicates' rowPtr arrays compete for GPU L2 cache space,
     the O(1) rowPtr reads may trigger L2 cache misses, making them
     slower than GPU_01's compact sorted arrays.

  c) Total GPU memory usage:
     GPU_01: stores only (s,o) pairs → minimal overhead.
     GPU_03: stores rowPtr (nEntities+1 per pred per direction) +
     colInd (≈ same size as pairs).
     For datasets with many predicates, GPU_03 uses significantly more
     GPU memory.

  d) Warp broadcast in coop kernel:
     All 32 lanes need the same key for the first atom.  GPU_01's
     binary search can be served by a single L2/texture cache line read
     and broadcast to all lanes.  The O(1) vs O(log n) difference
     matters less when the entire warp reads the same addresses.

11. WHAT CHANGES FROM GPU_01
===============================

  Data structure:
    OLD: sorted int2 arrays per predicate (PredHost / PredDev)
    NEW: CSR matrices per predicate (DevCSR / PredCSR)

  AtomGPU struct:
    OLD: const int2* arr; int n;  (sorted array + length)
    NEW: const int* rowPtr; const int* colInd;  (CSR pointers)

  DFS key lookup:
    OLD: lb(arr, a.n, key) + ub(arr, a.n, key)  — O(log |P|)
    NEW: __ldg(&rowPtr[key]) + __ldg(&rowPtr[key+1])  — O(1)

  DFS value access:
    OLD: __ldg(&a.arr[i].y)    — reads .y field of int2
    NEW: __ldg(&a.colInd[i])   — reads int from colInd array

  Head triples:
    OLD: from sorted int2 device array (same as SPO data)
    NEW: CompactHead built from PredIndex on host (no GPU round-trip)

  gpu_index.cuh:
    OLD: PredHost/PredDev with sorted int2, build_gpu_index(), upload()
    NEW: DevCSR/PredCSR with CSR, build_all_csr(), CompactHead

  Maxfan source:
    OLD: PredHost.spo_maxfan (computed from sorted int2)
    NEW: DevCSR.maxfan (computed from CSR rowPtr differences)

  GPU memory:
    OLD: 2 × nnz × sizeof(int2) per predicate
    NEW: 2 × [(nEntities+1) × sizeof(int) + nnz × sizeof(int)] per pred


12. WHAT CHANGES FROM GPU_02
===============================

  Algorithm:
    OLD: chain extraction + fused_support_kernel (runtime recursion)
    NEW: template DFS<L,N> with full variable binding (compile-time)

  Atom descriptors:
    OLD: DevChainCSR/DevExtraCheck passed via kernel arguments
    NEW: AtomGPU in __constant__ memory

  Kernel types:
    OLD: single fused kernel (1 thread per head triple)
    NEW: standard + warp-cooperative (32 lanes for high-fanout)

  Per-rule allocation:
    OLD: cudaMalloc/Free for chain/filter/extra arrays each rule
    NEW: zero allocation (only cudaMemcpyToSymbol to __constant__)

  Injective mapping:
    OLD: NOT enforced on chain intermediate variables
    NEW: fully enforced on all variables

  DevCSR struct:
    OLD: int rows, cols; int64_t nnz; int* d_rowPtr; int* d_colInd; bool ownsMemory;
    NEW: int rows, nnz; int* d_rowPtr; int* d_colInd; int maxfan;

  CompactHead construction:
    OLD: download CSR from GPU → expand → re-upload
    NEW: build directly from host-side PredIndex (no round-trip)
