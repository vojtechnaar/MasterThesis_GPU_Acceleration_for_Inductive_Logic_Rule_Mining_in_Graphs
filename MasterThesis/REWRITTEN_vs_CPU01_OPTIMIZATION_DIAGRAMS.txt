================================================================================
  OPTIMIZATION DIAGRAMS: Rewritten_CPP vs CPU_01_nonparallel
================================================================================
  This file contains detailed ASCII diagrams illustrating the 4 major
  optimizations applied when going from the faithful Scala port (Rewritten_CPP)
  to the cache-optimized version (CPU_01_nonparallel).

  Both implementations compute the same result (AMIE-style DFS support 
  counting with injective mapping). The difference is purely in data layout 
  and compilation strategy.

  Optimizations covered:
    1. Index layout:       nested hash maps  -->  CSR flat arrays
    2. Binding state:      heap vector        -->  stack-local fixed array
    3. Atom tracking:      vector<bool>       -->  uint8_t bitmask
    4. DFS dispatch:       generic recursion  -->  template<N> specialization


================================================================================
  OPTIMIZATION 1: INDEX LAYOUT — Hash Maps vs CSR Flat Arrays
================================================================================

  Both versions store the knowledge graph as two indexes per predicate:
    PSO  (predicate -> subject -> objects)   — for "subject is known, find objects"
    POS  (predicate -> object  -> subjects)  — for "object is known, find subjects"

  They differ in HOW those mappings are stored in memory.


  ---------- Rewritten_CPP: Nested Hash Maps ----------

  Source: Rewritten_CPP/RdfIndexes.hpp

    using IntVec = std::vector<int>;
    using SubjectToObjects = std::unordered_map<int, IntVec>;
    std::unordered_map<int, SubjectToObjects> pso;   // predicate -> subject -> {objects}
    std::unordered_map<int, ObjectToSubjects> pos;    // predicate -> object  -> {subjects}

  Memory layout (3 levels of indirection):

    pso (outer unordered_map)
    +--------+--------+--------+
    | pred=5 | pred=9 | pred=2 | ...       <-- hash buckets (scattered in heap)
    +---+----+---+----+---+----+
        |        |        |
        v        v        v
    SubjectToObjects (middle unordered_map, one per predicate)
    +--------+--------+--------+
    | subj=3 | subj=7 | subj=1 | ...       <-- more hash buckets (scattered)
    +---+----+---+----+---+----+
        |        |        |
        v        v        v
    IntVec (innermost vector, one per subject)
    +------+------+------+
    | obj=2| obj=5| obj=9| ...              <-- contiguous within this vector
    +------+------+------+                      but each vector is its own heap alloc

  Lookup: getObjects(pred=5, subj=3)
    Step 1: pso.find(5)        --> hash probe in outer map        (cache miss likely)
    Step 2: result.find(3)     --> hash probe in middle map       (cache miss likely)
    Step 3: return &vec        --> pointer to vector on heap       (cache miss likely)
    Total: ~3 pointer chases, each likely a cache miss.

  Build cost:
    - Each addTriple() does 2 hash lookups + possible rehash
    - finalize() sorts each IntVec independently
    - Many small heap allocations (one vector per (predicate, subject) pair)


  ---------- CPU_01_nonparallel: CSR (Compressed Sparse Row) ----------

  Source: CPU_01_nonparallel/RdfIndexes.hpp

    struct PredIndex {
        std::vector<std::pair<int,int>> spo;   // sorted (subject, object) pairs
        std::vector<int> spoKeys;       // sorted unique subjects
        std::vector<int> spoOffsets;    // spoKeys.size()+1 entries
        std::vector<int> spoVals;       // objects per subject (sorted)
        // ... same for pos (posKeys, posOffsets, posVals)
    };
    std::unordered_map<int, PredIndex> predIndexes;   // one PredIndex per predicate

  Memory layout (CSR = 3 flat arrays per direction):

    predIndexes[5] --> PredIndex for predicate 5
    +---------------------------------------------------------------------------+
    |                                                                           |
    |  spoKeys:   [ 1,    3,      7,       12  ]    (sorted unique subjects)    |
    |               |     |       |         |                                   |
    |  spoOffsets:[ 0,    2,      5,        7,    9 ]   (cumulative offsets)     |
    |               |     |       |         |     |                             |
    |  spoVals:   [ 4, 8, 2, 5, 9, 1, 3, 6, 5, 7 ]   (objects, contiguous)     |
    |              |___|  |______|  |____|  |____|                              |
    |             subj=1   subj=3   subj=7  subj=12                             |
    |                                                                           |
    +---------------------------------------------------------------------------+

    Reading the diagram:
      subj=1 has objects at spoVals[0..2) = {4, 8}
      subj=3 has objects at spoVals[2..5) = {2, 5, 9}
      subj=7 has objects at spoVals[5..7) = {1, 3, 6}   (wait, that's 3 but 7-5=2)
      ... (actual counts depend on data, this is illustrative)

  Lookup: spoRange(subj=3)
    Step 1: binary_search(spoKeys, 3) --> index i=1           (NO hash, sorted array)
    Step 2: begin = spoVals + spoOffsets[1] = spoVals + 2     (pointer arithmetic)
    Step 3: count = spoOffsets[2] - spoOffsets[1] = 5 - 2 = 3 
    Step 4: return (begin, count)                              (contiguous memory!)
    Total: 1 binary search on contiguous array, then direct pointer. Cache-friendly.

  Build cost (one-time, in buildIndexes()):
    1. Collect all (subject, object) pairs per predicate
    2. Sort pairs by subject
    3. Scan sorted pairs to extract unique subjects -> spoKeys
    4. Record offsets where each subject's objects begin -> spoOffsets
    5. Copy all objects into flat array -> spoVals
    Result: 3 contiguous arrays, zero per-subject heap allocations


  ---------- Comparison ----------

    +------------------+----------------------------+----------------------------+
    | Aspect           | Rewritten_CPP (Hash Maps)  | CPU_01 (CSR Flat Arrays)   |
    +------------------+----------------------------+----------------------------+
    | Data structure   | unordered_map<int,          | 3 flat vectors:            |
    |                  |   unordered_map<int,        |   spoKeys, spoOffsets,     |
    |                  |     vector<int>>>           |   spoVals                  |
    +------------------+----------------------------+----------------------------+
    | Lookup method    | Hash probe -> hash probe    | Binary search on sorted    |
    |                  | -> vector pointer           | array -> pointer arithmetic|
    +------------------+----------------------------+----------------------------+
    | Cache behavior   | 3 pointer chases across     | 1 binary search in         |
    |                  | scattered heap memory       | contiguous memory          |
    +------------------+----------------------------+----------------------------+
    | Memory overhead  | Hash table overhead per     | 3 flat arrays              |
    |                  | level (~1.5-2x for buckets) | (minimal overhead)         |
    +------------------+----------------------------+----------------------------+
    | Build cost       | Incremental (add one at     | Batch: sort + scan         |
    |                  | a time), many small allocs  | (one-time, efficient)      |
    +------------------+----------------------------+----------------------------+


================================================================================
  OPTIMIZATION 2: BINDING STATE — Heap Vector vs Stack-Local Fixed Array
================================================================================

  During DFS backtracking, the algorithm maintains a mapping from variable IDs
  to concrete entity IDs. Each recursion level may bind a new variable, and
  must unbind it on backtrack.


  ---------- Rewritten_CPP: Heap-Allocated BindingMap ----------

  Source: Rewritten_CPP/SupportCounting.hpp

    struct BindingMap {
        std::vector<int> hmap;             // variable index -> constant ID, -1 = unbound
        UsedTriple usedAtoms[MAX_USED_ATOMS];
        int usedCount = 0;
        bool injectiveMapping = true;

        BindingMap() : hmap(4, -1), usedCount(0) {}   // pre-allocate for 4 variables
    };

  Memory layout:

    Stack frame of bodyExistsRecursive()
    +--------------------+
    | BindingMap binding  |  <-- struct on stack, BUT...
    |   .hmap  --------+-+---> Heap allocation (std::vector internal buffer)
    |   .usedAtoms[8]   |      +-----+-----+-----+-----+
    |   .usedCount       |      | v0= | v1= | v2= | v3= |  (variable bindings)
    |   .injectiveMapping|      | 42  | -1  | 107 | -1  |
    +--------------------+      +-----+-----+-----+-----+
                                    ^
                                    |
                                 Heap memory (may be far from stack)

  On each DFS call:
    - BindingMap is COPIED from parent frame (copy constructor)
    - std::vector copy = new heap allocation + memcpy of contents
    - On backtrack: manual hmap[varId] = savedValue (restore)
    - Vector may need to resize if varId >= hmap.size()

  Cost per DFS level:
    - 1 heap allocation (vector copy)
    - 1 heap deallocation (when BindingMap goes out of scope)
    - Possible cache miss accessing heap-allocated hmap data


  ---------- CPU_01_nonparallel: Stack-Local Env ----------

  Source: CPU_01_nonparallel/SupportCounting.hpp

    static constexpr int MAX_VARS = 16;
    static constexpr int MAX_USED = 9;

    struct Env {
        int v[MAX_VARS];              // 0 = unbound, constId+1 = bound
        UsedTriple used[MAX_USED];
        int usedCount;

        void init() { std::memset(v, 0, sizeof(v)); usedCount = 0; }
        bool isBound(int varId) const  { return v[varId] != 0; }
        int  resolve(int varId) const  { return v[varId] - 1; }
        void bind(int varId, int cid)  { v[varId] = cid + 1; }
    };

  Memory layout:

    Stack frame of countSupport() — Env lives here for the ENTIRE DFS tree
    +---------------------------------------------------+
    | Env env;                                          |
    |   .v[0]  .v[1]  .v[2]  ... .v[15]                |
    |   [ 43 ] [  0 ] [108 ]     [  0  ]               |   <-- ALL on stack
    |                                                   |
    |   .used[0]       .used[1]       ... .used[8]      |
    |   {s=42,p=5,o=7} {s=1,p=9,o=3}     {0,0,0}       |   <-- ALL on stack
    |                                                   |
    |   .usedCount = 2                                  |
    +---------------------------------------------------+
           ^
           |
        Stack memory (hot in L1 cache, always nearby)

  On each DFS level:
    - NO allocation, NO copy
    - Bind:     env.v[varId] = cid + 1;           (1 array write)
    - Backtrack: env.v[varId] = savedValue;         (1 array write)
    - The SAME Env instance is passed by reference through all recursion levels

  Encoding trick:
    - 0 means "unbound" (so constant ID 0 is stored as 0+1 = 1)
    - This avoids needing a separate "is-bound" flag
    - bind(varId, cid) stores cid+1; resolve(varId) returns v[varId]-1


  ---------- Comparison ----------

    +-------------------+-----------------------------+----------------------------+
    | Aspect            | Rewritten_CPP (BindingMap)  | CPU_01 (Env)               |
    +-------------------+-----------------------------+----------------------------+
    | Storage           | std::vector<int> on heap    | int v[16] on stack         |
    +-------------------+-----------------------------+----------------------------+
    | Allocation        | 1 heap alloc per DFS copy   | Zero allocations ever      |
    +-------------------+-----------------------------+----------------------------+
    | Backtrack cost    | Restore saved value          | Restore saved value        |
    |                   | (same, but on heap memory)   | (same, but on stack/L1)    |
    +-------------------+-----------------------------+----------------------------+
    | Cache locality    | Heap pointer chase           | Always in L1/L2 cache      |
    +-------------------+-----------------------------+----------------------------+
    | Max variables     | Unlimited (vector resizes)   | Fixed 16 (sufficient for   |
    |                   |                              | all real-world rules)      |
    +-------------------+-----------------------------+----------------------------+
    | Unbound sentinel  | -1                           | 0 (with +1 encoding)       |
    +-------------------+-----------------------------+----------------------------+
    | sizeof            | ~80+ bytes (vector metadata  | 100 bytes fixed            |
    |                   | + heap data elsewhere)       | (64 + 36 = on stack)       |
    +-------------------+-----------------------------+----------------------------+


================================================================================
  OPTIMIZATION 3: ATOM TRACKING — vector<bool> vs uint8_t Bitmask
================================================================================

  During DFS, the algorithm must track which body atoms have already been
  matched (to avoid matching the same atom twice in a single DFS path).


  ---------- Rewritten_CPP: vector<bool> ----------

  Source: Rewritten_CPP/SupportCounting.cpp

    bool SupportCounting::bodyExists(...) const {
        std::vector<bool> used(body.size(), false);   // one bool per body atom
        ...
        return bodyExistsRecursive(body, used, binding, 0);
    }

    bool SupportCounting::bodyExistsRecursive(...) {
        used[bestIndex] = true;     // mark atom as matched
        ...                          // recurse
        used[bestIndex] = false;    // backtrack: unmark
    }

  Memory layout for a 3-body-atom rule:

    std::vector<bool> used;     (special STL bit-packed vector)
    +-----------------------------+
    | vector metadata (on stack): |
    |   .data ------+             |
    |   .size = 3   |             |
    +-----------------------------+
                    |
                    v
    Heap-allocated bit storage:
    +-----+-----+-----+-----+--- ... ---+
    | b0  | b1  | b2  | pad | ...       |    <-- typically 1 word minimum
    +-----+-----+-----+-----+--- ... ---+
      ^                                       Note: vector<bool> is special —
      |                                       it packs bits, NOT bytes. Each
      Heap memory                             access requires bit manipulation.

  Operations:
    - Check:     used[i]       --> heap access + bit extraction
    - Set:       used[i]=true  --> heap access + bit-OR
    - Clear:     used[i]=false --> heap access + bit-AND
    - Iteration: for(i=0; i<n; i++) if(!used[i])  --> n heap accesses

  Problems:
    1. Heap allocation for the vector's internal storage (even for 3 bits!)
    2. vector<bool> is notoriously slow due to bit-packing proxy objects
    3. Passed by reference between recursion levels (not terrible, but...)
    4. "Find next unmatched atom" requires a linear scan


  ---------- CPU_01_nonparallel: uint8_t Bitmask ----------

  Source: CPU_01_nonparallel/SupportCounting.hpp

    template<int N>
    bool dfsExists(const Atom* body, uint8_t remaining, Env& env, int matched) const;

  The entire "which atoms are still available" state is a single byte:

    uint8_t remaining = 0b00000111;     // for 3 body atoms: bits 0,1,2 set
                                         // means atoms 0, 1, 2 are still available

    Bit layout (example: 3 body atoms):
    +----+----+----+----+----+----+----+----+
    | b7 | b6 | b5 | b4 | b3 | b2 | b1 | b0 |
    +----+----+----+----+----+----+----+----+
    |  0 |  0 |  0 |  0 |  0 |  1 |  1 |  1 |  = 0x07 = all 3 available
    +----+----+----+----+----+----+----+----+
                                ^    ^    ^
                              atom2 atom1 atom0

  Operations (all single CPU instructions, no memory access):
    - Initialize:  uint8_t all = (1 << n) - 1;           // e.g., 0b111 for n=3
    - Check:       remaining & (1 << i)                   // is atom i available?
    - Remove:      nextRemaining = remaining & ~(1 << i)  // mark atom i as matched
    - No "unmark" needed — just pass the old 'remaining' value to parent frame
    - Find available: loop over bits (at most 8 iterations, no memory access)

  Example DFS flow for 3 body atoms:

    dfsExists<3>(body, remaining=0b111, env, matched=0)
        chooseBestAtom picks atom 1
        --> dfsExists<3>(body, remaining=0b101, env, matched=1)
            chooseBestAtom picks atom 2
            --> dfsExists<3>(body, remaining=0b001, env, matched=2)
                chooseBestAtom picks atom 0
                --> dfsExists<3>(body, remaining=0b000, env, matched=3)
                    matched == N --> return true!

    At each level, 'remaining' is passed BY VALUE (uint8_t = 1 byte on stack).
    Backtracking is FREE — the parent's 'remaining' is never modified.


  ---------- Comparison ----------

    +-------------------+----------------------------+----------------------------+
    | Aspect            | Rewritten_CPP (vector<bool>)| CPU_01 (uint8_t bitmask)  |
    +-------------------+----------------------------+----------------------------+
    | Storage           | Heap-allocated bit vector   | 1 byte on stack            |
    +-------------------+----------------------------+----------------------------+
    | Allocation        | 1 heap alloc per bodyExists | Zero allocations           |
    +-------------------+----------------------------+----------------------------+
    | Mark matched      | used[i] = true (heap write  | remaining & ~(1<<i)        |
    |                   | + bit manipulation)          | (register operation)       |
    +-------------------+----------------------------+----------------------------+
    | Backtrack         | used[i] = false (heap write) | Automatic (value on stack) |
    +-------------------+----------------------------+----------------------------+
    | "Any remaining?"  | Linear scan O(n)            | remaining != 0 (1 instr)   |
    +-------------------+----------------------------+----------------------------+
    | Max body atoms    | Unlimited                   | 8 (uint8_t = 8 bits)       |
    |                   |                              | Sufficient for all real    |
    |                   |                              | rules (bodies <= 8 atoms)  |
    +-------------------+----------------------------+----------------------------+
    | sizeof            | 24+ bytes (vector metadata)  | 1 byte                    |
    +-------------------+----------------------------+----------------------------+


================================================================================
  OPTIMIZATION 4: DFS DISPATCH — Generic Recursion vs Template Specialization
================================================================================

  Both versions use depth-first search with backtracking to check if at least
  one satisfying binding exists for the body atoms. They differ in how the
  recursion is compiled.


  ---------- Rewritten_CPP: Generic Runtime Recursion ----------

  Source: Rewritten_CPP/SupportCounting.cpp

    bool bodyExistsRecursive(
        const std::vector<Atom>& body,   // body passed by reference (any size)
        std::vector<bool>& used,          // tracking (any size)
        BindingMap& binding,              // bindings (any size)
        int matchedCount                  // how many matched so far
    ) const {
        if (matchedCount == body.size()) return true;   // base case: runtime check
        ...
        return bodyExistsRecursive(body, used, binding, matchedCount + 1);
    }

  What the compiler sees:

    bodyExistsRecursive() is ONE function that handles ALL body sizes.

    Compiler cannot know at compile time:
      - How many atoms are in the body
      - How deep the recursion will go
      - Whether matchedCount == body.size() will be true

    Consequences:
    +------------------------------------------------------------------+
    | Source code:                                                      |
    |   bool bodyExistsRecursive(body, used, binding, matchedCount)     |
    |                                                                   |
    | Compiled to:  ONE machine code function                           |
    |                                                                   |
    |   bodyExistsRecursive:                                            |
    |     cmp matchedCount, [body.size]    ; runtime comparison         |
    |     je  .return_true                                              |
    |     ...                                                           |
    |     call bodyExistsRecursive         ; indirect/conditional jump  |
    |     ...                                                           |
    |                                                                   |
    | The compiler CANNOT:                                              |
    |   - Unroll the recursion (unknown depth)                          |
    |   - Inline the recursive call (self-referential)                  |
    |   - Eliminate the matchedCount==size check (always needed)         |
    |   - Specialize variable binding patterns per depth                |
    +------------------------------------------------------------------+


  ---------- CPU_01_nonparallel: Template<N> Specialization ----------

  Source: CPU_01_nonparallel/SupportCounting.hpp

    template<int N>
    bool dfsExists(const Atom* body, uint8_t remaining, Env& env, int matched) const;

  Source: CPU_01_nonparallel/SupportCounting.cpp

    bool SupportCounting::bodyExists(const Atom* body, int n, Env& env) const {
        uint8_t all = (uint8_t(1) << n) - 1;
        switch (n) {
            case 1: return dfsExists<1>(body, all, env, 0);
            case 2: return dfsExists<2>(body, all, env, 0);
            case 3: return dfsExists<3>(body, all, env, 0);
            case 4: return dfsExists<4>(body, all, env, 0);
            case 5: return dfsExists<5>(body, all, env, 0);
            case 6: return dfsExists<6>(body, all, env, 0);
            case 7: return dfsExists<7>(body, all, env, 0);
            case 8: return dfsExists<8>(body, all, env, 0);
            default: return false;
        }
    }

  What the compiler sees:

    For each N, the compiler generates a SEPARATE optimized function:

    +------------------------------------------------------------------+
    | template<int N=1>  -->  dfsExists_1:                              |
    |   "if (matched == 1)" is known at compile time                   |
    |   Compiler can fully inline the single-atom check                |
    |   No recursion needed (trivial case)                             |
    +------------------------------------------------------------------+
    | template<int N=2>  -->  dfsExists_2:                              |
    |   "if (matched == 2)" — compiler knows max depth is 2            |
    |   Can inline dfsExists<2>(matched=1) inside dfsExists<2>(m=0)   |
    |   Loop unrolling possible for 2 atoms                            |
    +------------------------------------------------------------------+
    | template<int N=3>  -->  dfsExists_3:                              |
    |   Compiler generates code knowing exactly 3 atoms exist          |
    |   Bitmask operations on 3 bits can be simplified                 |
    |   Recursion depth limited to 3 — aggressive inlining possible    |
    +------------------------------------------------------------------+
    |   ...and so on for N=4,5,6,7,8                                   |
    +------------------------------------------------------------------+

  Benefits of template specialization:

    1. COMPILE-TIME CONSTANT N:
       The comparison "if (matched == N)" uses a compile-time constant.
       The compiler can optimize branches that are impossible.

    2. INLINING:
       dfsExists<3> calling dfsExists<3> is a self-call at the SAME N,
       but the compiler can inline it because the recursion depth is bounded.

    3. BITMASK OPTIMIZATION:
       With N known at compile time, the initial bitmask (1<<N)-1 is a constant.
       Bit operations can be simplified by the optimizer.

    4. BRANCH PREDICTION:
       Separate functions for each N have different branch history,
       leading to better CPU branch prediction.


  ---------- Visual: What Gets Compiled ----------

  Rewritten_CPP — ONE function handles all rule sizes:

    +-----------------------------------------+
    |  bodyExistsRecursive()     [1 function]  |
    |                                          |
    |  handles: 1-atom rules                   |
    |           2-atom rules                   |
    |           3-atom rules                   |
    |           ... any size                   |
    |                                          |
    |  Runtime checks needed at every call:    |
    |    - Is matchedCount == body.size()?      |
    |    - Which atoms are still unused?        |
    |    - How big is the body vector?          |
    +-----------------------------------------+

  CPU_01_nonparallel — EIGHT specialized functions:

    +------------------+  +------------------+  +------------------+
    |  dfsExists<1>()  |  |  dfsExists<2>()  |  |  dfsExists<3>()  |
    |  Optimized for   |  |  Optimized for   |  |  Optimized for   |
    |  single-atom     |  |  two-atom        |  |  three-atom      |
    |  bodies          |  |  bodies          |  |  bodies          |
    +------------------+  +------------------+  +------------------+

    +------------------+  +------------------+  ...
    |  dfsExists<4>()  |  |  dfsExists<5>()  |
    |  Optimized for   |  |  Optimized for   |
    |  four-atom       |  |  five-atom       |
    |  bodies          |  |  bodies          |
    +------------------+  +------------------+

    bodyExists() dispatches to the right one via switch(n):
    +-----------------------------+
    |  bodyExists(body, n, env)   |
    |    switch(n):               |
    |      1 -> dfsExists<1>()   |
    |      2 -> dfsExists<2>()   |
    |      3 -> dfsExists<3>()   |   <-- one-time branch, then all
    |      4 -> dfsExists<4>()   |       subsequent calls are within
    |      5 -> dfsExists<5>()   |       the specialized function
    |      ...                    |
    +-----------------------------+


  ---------- Comparison ----------

    +-------------------+----------------------------+----------------------------+
    | Aspect            | Rewritten_CPP (Generic)    | CPU_01 (Template<N>)       |
    +-------------------+----------------------------+----------------------------+
    | Functions compiled| 1 generic function         | 8 specialized functions    |
    +-------------------+----------------------------+----------------------------+
    | Base case check   | Runtime: matched==body.size| Compile-time: matched==N   |
    +-------------------+----------------------------+----------------------------+
    | Inlining          | Cannot inline self-call    | Compiler can inline        |
    |                   | (unbounded recursion)       | (bounded depth N)          |
    +-------------------+----------------------------+----------------------------+
    | Binary size       | Smaller (1 function)       | Larger (8 copies)          |
    +-------------------+----------------------------+----------------------------+
    | Branch prediction | All sizes share same       | Each N has its own branch  |
    |                   | branch history             | history (better prediction)|
    +-------------------+----------------------------+----------------------------+
    | Flexibility       | Any body size              | Max 8 body atoms           |
    |                   |                             | (sufficient in practice)   |
    +-------------------+----------------------------+----------------------------+
    | Code complexity   | Simple, readable           | More complex (template     |
    |                   |                             | + switch dispatch)         |
    +-------------------+----------------------------+----------------------------+


================================================================================
  COMBINED EFFECT ON A SINGLE SUPPORT-COUNT CALL
================================================================================

  For a rule like:  p(?a, ?b) <-- q(?a, ?c), r(?c, ?b)   (1 head + 2 body atoms)

  Rewritten_CPP execution flow (per head binding):
    1. Allocate BindingMap on stack (but hmap vector allocs on HEAP)
    2. matchHeadAtom -> bind ?a, ?b in hmap (heap write)
    3. bodyExists:
       a. Allocate vector<bool> used(2, false) on HEAP
       b. Copy BindingMap (HEAP alloc for vector copy)
       c. chooseBestAtomIndex: scan used[] (HEAP reads)
       d. indexes_.pso.find(pred) -> HASH probe (cache miss)
       e. result.find(subject) -> HASH probe (cache miss)
       f. Iterate objects vector (HEAP, possibly cache miss)
       g. For each candidate: recurse -> repeat from (b)
    4. On backtrack: restore hmap entries, used[i]=false (HEAP writes)

  CPU_01_nonparallel execution flow (per head binding):
    1. Env.init() -> memset 100 bytes on STACK (hot in L1)
    2. matchHeadAtom -> bind ?a, ?b in env.v[] (STACK write)
    3. bodyExists -> switch(2) -> dfsExists<2>:
       a. remaining = 0b11 (REGISTER, 1 byte)
       b. NO copy of Env (passed by reference, same stack memory)
       c. chooseBestAtom: check remaining bits (REGISTER ops)
       d. indexes_.getPred(pred) -> 1 hash lookup (only outer level)
       e. binary_search(spoKeys, subject) (CONTIGUOUS array in cache)
       f. Iterate spoVals[offset..offset+count] (CONTIGUOUS, cache-friendly)
       g. For each candidate: recurse with nextRemaining (REGISTER)
    4. On backtrack: env.v[varId] = saved (1 STACK write)


  Performance impact summary per DFS node:

    +-------------------------+------------------+------------------+
    |                         | Rewritten_CPP    | CPU_01           |
    +-------------------------+------------------+------------------+
    | Heap allocations        | 2-3              | 0                |
    | Cache misses (likely)   | 3-4              | 0-1              |
    | Hash probes             | 2                | 0 (binary search)|
    | Memory touched          | Scattered heap   | Stack + 3 arrays |
    +-------------------------+------------------+------------------+

  The optimizations are MULTIPLICATIVE — each DFS node visits fewer cache 
  lines and does zero allocations, and there can be millions of DFS nodes 
  per rule. On a 500-rule benchmark, this compounds to significant speedup.
